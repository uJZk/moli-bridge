# FlareSolverr bridge investigation

## Compatibility target

The required integration is [MoviePilot sehuatangsignin](https://github.com/Vivitoto/MoviePilot-Plugins/tree/7c7d1036423f3e7350f307c7ad87bd6d2044712a/plugins.v3/sehuatangsignin), examined at commit `7c7d1036423f3e7350f307c7ad87bd6d2044712a`. The default site is `https://sehuatang.net`, configurable by the plugin. Its `captcha_server.py` uses `sessions.create` with `maxTimeout` and an optional proxy object; `sessions.destroy`; and `request.get` with a session, URL, timeout, cookies, optional headers and proxy. It requires an `ok` response and a session ID, consumes `solution.response`, `solution.cookies`, `solution.status` and `solution.userAgent`, and merges returned cookies into its account jar. Its POST helper does **not** use `request.post`: it first uses a separately launched browser for same-origin fetch, then falls back to direct Python HTTP. Other plugin flows also launch and retain their own browser sessions. The bridge cannot by itself make those separate execution paths use Moli or establish end-to-end compatibility.

The executable checks in [tools/flaresolverr-contract](../tools/flaresolverr-contract/README.md) exercise the actual plugin API helpers and a local HTTP proxy. In an isolated container network, fixtures verified unauthenticated and Basic-authenticated proxy requests, password escaping, TTL rotation with a one-process limit, and incorrect-credential rejection without direct fallback. Site access, other proxy protocols, the plugin's independent browser paths and a complete sign-in still need real integration tests.

## Jackett integration

Jackett commit `ffe6cd64391787612967a2cd28850970720d9fe3` uses FlareSolverrSharp 4.0.0. Its `ClearanceHandler` first makes the request itself; on a recognized Cloudflare or DDoS-Guard challenge it calls the FlareSolverr API, requires a nonempty cookie array, takes the returned user agent, retains cookies whose names start with `cf_`, `__cf` or `__ddg`, and retries the original request. It does not substitute `solution.response` for that final Jackett response. A nonempty array containing only unrelated cookies therefore does not establish clearance.

[`check-jackett-sharp.py`](../tools/flaresolverr-contract/check-jackett-sharp.py) runs the real FlareSolverrSharp 4.0.0 package against a local fixture and the bridge. It checks cookie and user-agent handoff and the real client's error behavior for absent and unrelated cookies. This verifies the handoff, not Jackett's full indexer, a remote site's challenge, or network/IP identity across deployments. FlareSolverrSharp is MIT licensed; it is restored from NuGet for this test and not included in the bridge image.

The same local test checks two DataDome limitations in that client: a response with only DataDome's `x-dd-b` signal does not trigger a FlareSolverr call, and a `datadome` cookie returned after a separately recognized challenge is not copied into the retry. Consequently, the bridge's DataDome support does not by itself establish Jackett DataDome compatibility. An [optional source patch](../tools/jackett/README.md) adds both handoff steps; its separately versioned package passed the local client fixture and a complete build of the pinned Jackett server. In a container without external network, the built server also completed Torznab searches against local Cloudflare and DataDome fixtures using the TorrentKitty parsing rules. It has not been tested against a live site. These observations are specific to the tested versions and fixtures, not claims about every Jackett release or other FlareSolverr clients.

## Upstream candidate

[TRAWL](https://github.com/germondai/trawl) was examined at commit `38e4b21de1061ea531cf711fec5efa5ac46ef9ee` (2026-11-15). Its license is AGPL-3.0; a distributed or network-accessible modified TRAWL must be reviewed for the applicable source and notice obligations. The bridge adapts TRAWL request-budget and Cloudflare title matching code, the challenge waiter's two-observation approach, and a limited POST replay guard; their source and AGPL-3.0 license are retained in `flaresolverr-bridge/upstream/`. The bridge package and container identify as AGPL-3.0-only; the Moli workspace and other components retain their own licenses. Deployment and redistribution must satisfy the applicable corresponding-source obligations. The prototype reuses `playwright-core` and separately adapts FlareSolverr challenge detection patterns and its keyboard/button verification action under the upstream MIT license. This is partial parity; `tabs_till_verify` and token extraction are exercised with local verify-button and generic-button fixtures, but real protected-site behavior remains unverified. Moli 1.1.26 incorrectly puts hidden inputs into keyboard focus order; the bridge temporarily excludes main-document hidden inputs for explicit Tab-based verification. The current workspace build already excludes the hidden input in the same fixture.

At that revision `apps/api/src/routes/v1.ts` implements create/list/destroy, returns `session`, and maps GET/POST, cookies, headers, timeouts and proxy settings through its FlareSolverr adapter. Its own tests cover lifecycle and cookies. Unknown sessions are implicitly created by requests; destroying an unknown session returns an error. Its session implementation uses browser contexts and binds the proxy when a session is created. The response currently sets solution headers to an empty object. These are upstream observations, not Moli compatibility claims.

TRAWL's `packages/browser/src/pool.ts` launches Camoufox through `camoufox-js`; fresh contexts, Firefox preferences, proxy configuration and challenge solvers depend on that environment. For example, some evaluation uses Camoufox's `mw:` prefix. Replacing only the launch call with Playwright `connectOverCDP` would not establish equivalent behavior. A prototype must verify context lifecycle, cookie/POST/header handling, request proxy isolation and each required challenge path against Moli before selecting a reuse strategy. Keep any adaptation as a small, version-pinned upstream patch or contribution rather than a wholesale fork if feasible.

## Dynamic layout and RSSHub

The [dynamic-layout probe](../tools/rsshub/check-dynamic-table-layout.mjs) reproduces stale geometry in the official Moli 1.1.26 binary and a local debug build of this repository's `cc2b2fc2a` baseline without default allocator features. After a click inserts a table row and an ordinary block and changes an existing block's width, both new elements report zero rectangles and the existing block reports its old width. The same fixture returns current geometry in Chromium. `Page.getLayoutMetrics` leaves the Moli snapshot stale; a one-pixel screenshot publishes a current snapshot. This evidence isolates a general layout-publication limitation, not a table parser problem.

The renderer deliberately serves synchronous geometry from the last published snapshot, as documented in [layout_snapshot.rs](../moli-renderer-v8/src/native_bridge/context_host/layout_snapshot.rs). A general fix must define and test when asynchronous rendering publishes new layout, including frame ownership and resource costs; blindly refreshing every geometry read would change that contract. The optional [RSSHub UPS patch](../tools/rsshub/README.md) waits for nonempty status fields in the currently present rows and performs one in-memory 1×1 capture before the original visibility check. Local fixtures including hidden and visible loading placeholders pass; this is not a fix to the Moli rendering lifecycle or a live-site result, and it cannot predict later rows.

Three source-build experiments were evaluated without changing the workspace renderer. Publishing after animation-frame callbacks fixed the explicit animation-frame probe but not the unmodified UPS route. Publishing after all selected callback tasks made that route pass but did not fix visibility polling after a synchronous click. Refreshing a stale snapshot before external `Runtime.evaluate` or `Runtime.callFunctionOn` made both the dynamic visibility probe and the unmodified UPS fixture pass, including the seven real RSSHub module tests. However, it violated the existing frozen-layout contract: the `layout-policy` CDP smoke group failed, while the same group passed on the unmodified source build. A CSSOM-only `insertRule` change also remained stale. That experiment is not integrated; any future opt-in rendering mode needs an explicit contract and broader lifecycle, style, performance and isolation checks.

## Isolation and deployment gate

The user selected a single-container deployment for the Playwright gateway and bridge. Each endpoint launches its own Moli processes, but both share the container network and resource limits; no resource or control-plane isolation is claimed.

The bridge prototype has passed local fixture and plugin-helper checks, including an HTTP proxy, against Moli 1.1.26. A direct request to the default site failed in this environment before a page was retrieved; no challenge-solving or complete sign-in success is established. The initial [container workflow](https://github.com/uJZk/moli-bridge/actions/runs/44264718785) passed AMD64 and ARM64 (QEMU) smoke tests and published an `edge` image for source commit `0797a327a42eddbaff7b27aefd398810747ac7f5`. Its AMD64 image was pulled and passed the same local smoke test. That historical image used the official Moli 1.1.26 binary. The updated workflow targets `ghcr.io/ujzk/moli-bridge:latest` and builds Moli from this repository for both architectures, while smoke-testing AMD64 only; verify the workflow result before treating that image as published.
